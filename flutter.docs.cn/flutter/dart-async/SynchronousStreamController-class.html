SynchronousStreamController

SynchronousStreamController<T> 类 抽象 interface

一种会同步分发事件的流控制器。

同步流控制器适用于这样的情况：已有的异步事件触发了流上的另一个事件。

事件不会被添加到数据流中并等到之后的微任务才分发（这会增加延迟），而是由同步流控制器立即触发，就像该流事件就是当前事件或微任务一样。

同步流控制器可能会违反 Stream 的约定，因此必须谨慎使用以避免这种情况。

使用 SynchronousStreamController 而非普通 StreamController 的唯一优势是延迟更低。只有在延迟改善显著且使用安全时，才应使用同步版本。否则应使用普通流控制器；它始终能确保 Stream 行为正确，也不会意外破坏其他代码。

向同步控制器添加事件应当是处理原始事件的最后一步。此时，将事件添加到流中等同于返回事件循环，并在下一个微任务中添加该事件。

每个侦听器回调都会像顶层事件或微任务一样运行。这意味着如果回调抛出异常，系统会尽快将其报告为未捕获错误。因此，应在处理原始事件的最后添加事件：添加事件后执行的任何操作，都会延迟报告侦听器回调中的错误。

如果在无法确定当前是否处于另一个事件处理过程中的位置添加事件，流侦听器可能会在尚未准备好处理时就收到该事件。我们保证，调用 Stream.listen 后，在执行侦听的代码完成前不会收到任何事件。若对来源未知的函数调用作出响应时调用 add，就可能违反这一保证。

控制器的 onListen 回调不是异步事件，因此在 onListen 回调中向控制器添加事件始终是错误的。事件会在侦听器收到订阅之前就被分发。

同步广播流控制器还受到普通流控制器没有的一项限制：分发事件期间不得调用 add、addError、close 或 addStream 方法。也就是说，如果控制器流的订阅回调触发了上述任一方法的调用，该调用就会失败。广播流可能有多个侦听器；如果在一个事件正在同步添加时又添加另一个事件，后一个事件可能先于前一个事件到达部分侦听器。为避免这种情况，前一个事件正在分发时不能添加新事件。这样可以保证第一次调用 add、addError 或 close 返回时，事件已完整分发，后续事件也会按正确顺序分发。

这仍然只保证事件已交付给订阅。如果订阅处于暂停状态，实际回调仍可能稍后才执行，事件会先由订阅缓冲。除暂停以及尚未交付的后续缓冲事件外，添加事件时会同步调用回调。

当另一个事件正在处理时，向同步单订阅流控制器添加事件可能会导致第二个事件延迟，无法同步分发；在该事件分发之前，控制器也不会按同步方式运行。
