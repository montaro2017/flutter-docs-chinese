KeyMessageHandler? keyMessageHandler
getter/setter 对

处理所有发送到 Flutter 的按键事件的全局入口。

此处理器已弃用并将被移除。请改用 HardwareKeyboard.addHandler/HardwareKeyboard.removeHandler。

典型应用会使用 WidgetsBinding。启动时，焦点系统会将此字段设为一个分发传入事件的函数（参见 FocusManager），将事件发送到焦点系统，包括 FocusNode.onKey、FocusNode.onKeyEvent 和 Shortcuts。在这种情况下，应用无需读取、赋值或调用此值。

高级用法中，应用可以“修补”此回调。详情见下文。

处理器与事件结果

大致而言，Flutter 会按以下阶段处理每个原生按键事件：

  1. Platform-side pre-filtering, sometimes used for IME.
  2. The key event system.
  3. The text input system.
  4. Other native components (possibly non-Flutter).

每个阶段都会产生一个称为“事件结果”的布尔值。结果为 true 时，表示该阶段已处理此事件，并阻止其传递到下一阶段。借助此机制，“Ctrl-C”等快捷键不会在文本字段中输入字符“C”；未被任何组件处理的快捷键也可以触发特殊提示（例如 macOS 上的“bonk”提示音）。

在第二阶段（即“按键事件系统”）中，事件会分发到多个目标：RawKeyboard 的监听器、HardwareKeyboard 的处理器，以及 keyMessageHandler。无论处理器返回什么结果，所有目标都会收到该事件。只要任一处理器的结果为 true，第二阶段的总体结果就为 true，并会停止事件继续传递。

另请参阅：

  • RawKeyboard.addListener, which adds a raw keyboard listener.
  • RawKeyboardListener, which is also implemented by adding a raw keyboard listener.
  • HardwareKeyboard.addHandler, which adds a hardware keyboard handler.

高级用法：手动赋值或修补

如果不使用焦点系统管理焦点，可将此属性设为一个 KeyMessageHandler；当平台不应继续传递事件时，该处理器应返回 true。如果此字段为 null，则假定 Flutter 未处理按键事件，结果为 false。

即使使用焦点系统，你可能仍需执行其功能范围之外的操作。这时可以将 keyMessageHandler 设为一个回调来修补原处理器：先执行自己的任务，再调用原回调（也可以完全不调用）。

对 keyMessageHandler 的修补无法撤销。应始终假设其他组件可能在你之前或之后修补此处理器。因此，你可能需要编写自己的全局通知管理器，以便添加和移除回调。

在 FocusManager 赋值回调之前，不应修补 keyMessageHandler。在组件生命周期中的任何时刻（例如 initState）或调用 WidgetManager.instance 后，都能确保该回调已完成赋值。

此示例展示了如何处理未被任何焦点处理器（例如 Shortcuts）处理的按键事件：通过修补 keyMessageHandler.

应用会打印出所有未被应用主体处理的按键事件。尝试在第一个文本字段中输入内容：这些按键未被 Shortcuts 处理，会发送给后备处理器并打印出来。再试试 Ctrl+A 等文本快捷键：KeyA 按下事件会作为快捷键处理，不会发送给后备处理器，因此也不会打印。

按键组件是 FallbackKeyEventRegistrar，这是实现可逆修补所必需的组件。FallbackFocus 和 FallbackFocusNode 也有助于识别组件树的结构。FallbackDemo 展示了如何在应用中使用这些组件。
