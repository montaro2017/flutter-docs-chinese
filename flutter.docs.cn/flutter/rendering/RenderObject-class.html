RenderObject 类 抽象

渲染树中的一个对象。

RenderObject 类层次结构是渲染库存在的核心基础。

RenderObject 有一个 parent，并包含一个名为 parentData 的槽位，父级 RenderObject 可在其中存储子项专属的数据，例如子项的位置。RenderObject 类还实现了基本的布局和绘制协议。

不过，RenderObject 类并未定义子项模型（例如节点有零个、一个还是多个子项），也未定义坐标系（例如子项采用笛卡尔坐标还是极坐标等），或特定的布局协议（例如布局是宽度输入、高度输出，还是约束输入、尺寸输出；父级是在子项布局之前还是之后设置其尺寸和位置；以及是否允许子项读取父级的 parentData 槽位）。

RenderBox 子类规定布局系统使用笛卡尔坐标。

生命周期

不再需要 RenderObject 时必须调用 dispose。对象的创建者负责释放它。通常创建者是 RenderObjectElement；该 element 卸载时会释放自己创建的对象。

调用 dispose 时，RenderObject 负责清理其持有的所有昂贵资源，例如 Picture 或 Image 对象。这也包括渲染对象直接创建的所有 Layer。基类的 dispose 实现会将 layer 属性置为 null；子类也必须将其直接创建的其他图层置为 null。

编写 RenderObject 子类

在大多数情况下，直接继承 RenderObject 过于复杂，以 RenderBox 为起点会更合适。不过，如果渲染对象不打算使用笛卡尔坐标系，就应直接继承 RenderObject。这样便可以通过创建新的 Constraints 子类，而不是使用 BoxConstraints，来定义自己的布局协议；也可以使用一套全新的对象和值来表示布局结果，而不局限于 Size。这种灵活性提高的代价是无法依赖 RenderBox 的功能。例如，RenderBox 实现了固有尺寸协议，可在不完整布局子项的情况下测量其尺寸；如果子项尺寸变化，父级会重新布局以适应新尺寸。要正确实现这一功能并不容易，也容易引入错误。

编写 RenderBox 的大多数经验同样适用于编写 RenderObject，因此建议先阅读 RenderBox 相关讨论作为背景。主要区别在布局和命中测试，因为这正是 RenderBox 重点专门化的部分。

布局

布局协议始于一个 Constraints 子类。有关如何编写 Constraints 子类的更多信息，请参阅 Constraints 中的说明。

performLayout 方法应获取并应用 constraints。布局算法的输出会保存为对象的字段，用于描述该对象在父级布局中的几何信息。例如，对于 RenderBox，输出就是 RenderBox.size 字段。只有在父级调用子项的 layout 时将 parentUsesSize 指定为 true，父级才应读取此输出。

渲染对象中任何会影响自身布局的内容发生变化时，都应调用 markNeedsLayout。

命中测试

命中测试比布局更开放，没有可供重写的固定方法，需要由你自行提供实现。

命中测试方法的整体行为应与 RenderBox 中所述的行为相似。主要区别在于，输入不一定是 Offset。向 HitTestResult 添加条目时，也可以使用其他 HitTestEntry 子类。调用 handleEvent 方法时，会传入添加到 HitTestResult 中的同一个对象，因此可以用它跟踪信息，例如命中点的精确坐标（坐标系由新的布局协议决定）。

从一种协议适配到另一种协议

通常，Flutter 渲染对象树的根节点是 RenderView。它只有一个子项，而且该子项必须是 RenderBox。因此，如果要在渲染树中使用自定义 RenderObject 子类，有两种选择：替换 RenderView 本身，或者让一个 RenderBox 将你的类作为子项（后一种方式更常见）。

此 RenderBox 子类负责将 box 协议转换为你的类所使用的协议。

具体来说，在命中测试时，它会重写 RenderBox.hitTest，并调用你在类中提供的命中测试方法。

同样，它会重写 performLayout，创建适用于你的类的 Constraints 对象，并将其传给子项的 layout 方法。

渲染对象之间的布局交互

通常，渲染对象的布局只应依赖其子项布局的输出，并且只有在调用 layout 时将 parentUsesSize 设为 true 才能如此。如果设为 true，那么只要要渲染子项，父级就必须调用该子项的 layout；否则，子项的布局输出发生变化时，父级不会收到通知。

渲染对象协议也可以传递额外信息。例如，在 RenderBox 协议中，可以查询子项的固有尺寸和基线几何信息。但如果这样做，只要这些额外信息发生变化，且父级在上一布局阶段使用过这些信息，子项就必须对父级调用 markNeedsLayout。有关实现示例，请参阅 RenderBox.markNeedsLayout 方法。该方法会重写 RenderObject.markNeedsLayout，这样父级查询过固有尺寸或基线信息后，只要子项的几何信息变化，父级就会被标记为需要布局。
