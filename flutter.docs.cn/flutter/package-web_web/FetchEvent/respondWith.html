FetchEvent 的 respondWith() 方法会阻止浏览器执行默认的 fetch 处理，并允许你自行提供一个解析为 Response 的 Promise。

大多数情况下，你可以提供接收方能够理解的任何响应。例如，如果请求由 img 发起，响应正文就必须是图像数据。出于安全原因，有几项全局规则：

  • You can only return Response objects of Response.type "opaque" if the fetchEvent.request object's request.mode is "no-cors". This prevents the leaking of private data.
  • You can only return Response objects of Response.type "opaqueredirect" if the fetchEvent.request object's request.mode is "manual".
  • You cannot return Response objects of Response.type "cors" if the fetchEvent.request object's request.mode is "same-origin".

指定资源的最终 URL

从 Firefox 59 开始，Service Worker 为 FetchEvent.respondWith 提供 Response 时，Response.url 的值会作为最终解析出的 URL，传递给被拦截的网络请求。如果 Response.url 的值为空字符串，则使用 Request.url 作为最终 URL。

过去所有情况下都会将 Request.url 用作最终 URL，提供的 Response.url 实际上会被忽略。

例如，如果 Service Worker 拦截了样式表或 Worker 脚本，提供的 Response.url 就会用于解析相对路径资源或 WorkerGlobalScope.importScripts 子资源加载（Firefox 错误 1222008）。

对于大多数类型的网络请求，此更改没有影响，因为你无法观察最终 URL。不过，少数情况下它确实会产生影响：

  • If a fetch is intercepted, then you can observe the final URL on the result's Response.url.
  • 如果拦截了 worker 脚本，最终 URL 会用于设置 self.location，并作为 worker 脚本中相对 URL 的基准 URL。
  • If a stylesheet is intercepted, then the final URL is used as the base URL for resolving relative loads.

请注意，针对 Window 和 HTMLIFrameElement 的导航请求不会使用最终 URL。HTML 规范处理导航重定向的方式最终会让生成的 Window.location 使用请求 URL。这意味着网站离线时仍可提供网页的“替代”视图，而无需更改用户可见的 URL。
