StatefulWidget 类 抽象

具有可变状态的 widget。

State 是一种信息：(1) 在构建 widget 时可以同步读取；(2) 在 widget 的生命周期内可能发生变化。widget 的实现者有责任确保状态变化时及时通知 State，通知方式是调用 State.setState。

有状态 widget 通过构建一组更具体描述用户界面的其他 widget，来描述用户界面的一部分。这个构建过程会递归进行，直到用户界面的描述完全具体（例如，完全由描述具体 RenderObject 的 RenderObjectWidget 组成）。

当所描述的用户界面部分会动态变化时，有状态 widget 很有用，例如其内部状态由时钟驱动，或取决于某些系统状态。对于只依赖对象自身配置信息和 widget 膨胀所在 BuildContext 的组合，可以考虑使用 StatelessWidget。

StatefulWidget 实例本身不可变，其可变状态存储在单独的 State 对象中（由 createState 方法创建），或存储在该 State 订阅的对象中，例如 Stream 或 ChangeNotifier 对象；这些对象的引用保存在 StatefulWidget 自身的 final 字段中。

每当框架膨胀 StatefulWidget 时，都会调用 createState。因此，如果该 widget 被插入树中的多个位置，同一个 StatefulWidget 可能关联多个 State 对象。同样，如果 StatefulWidget 从树中移除后又重新插入，框架会再次调用 createState 创建新的 State 对象，从而简化 State 对象的生命周期管理。

如果创建 StatefulWidget 的代码为其 key 使用了 GlobalKey，那么该 widget 在树中从一个位置移动到另一个位置时会保留同一个 State 对象。由于带有 GlobalKey 的 widget 在树中最多只能位于一个位置，因此使用 GlobalKey 的 widget 最多只有一个关联的 element（元素）。框架利用这一特性，在移动带有全局 key 的 widget 时，会将与该 widget 关联的（唯一）子树从旧位置移接到新位置，而不是在新位置重新创建子树。与 StatefulWidget 关联的 State 对象也会随子树一同移接，因此新位置会复用原有的 State 对象。但要符合移接条件，widget 必须在从旧位置移除的同一个动画帧内插入新位置。

性能注意事项

StatefulWidget 主要分为两类。

第一类会在 State.initState 中分配资源，并在 State.dispose 中释放资源，但不依赖 InheritedWidget，也不调用 State.setState。这类 widget 通常位于应用或页面的根部，并通过 ChangeNotifier、Stream 或其他类似对象与子 widget 通信。遵循这种模式的有状态 widget 成本相对较低（消耗的 CPU 和 GPU 周期较少），因为它们只构建一次，之后不会更新。因此，它们可以拥有较复杂、较深的 build 方法。

第二类是使用 State.setState 或依赖 InheritedWidget 的 widget。这些 widget 通常会在应用生命周期内多次重建，因此应尽量减少重建带来的影响。（它们也可能使用 State.initState 或 State.didChangeDependencies 并分配资源，但关键特征是会重建。）

可以采用以下几种技巧来减少重建有状态 widget 带来的影响：

  • 将状态下推到叶子节点。例如，如果页面上有一个不断走动的时钟，不要把状态放在页面顶部并在每次跳动时重建整个页面；可以创建专用的时钟 widget，让它只更新自身。

  • 尽量减少 build 方法及其创建的 widget 传递性地产生的节点数量。理想情况下，有状态 widget 只创建一个 widget，而且该 widget 是 RenderObjectWidget。（实际中并非总能做到，但越接近这一理想，效率就越高。）

  • 如果子树不会变化，就缓存表示该子树的 widget，并在需要时重复使用。可以将 widget 赋给一个 final 状态变量，并在 build 方法中复用。复用 widget 的效率远高于重新创建一个配置相同的 widget。另一种缓存策略是将 widget 中可变的部分提取为一个接收 child 参数的 StatefulWidget。

  • 尽可能使用 const widget。（这相当于缓存并复用 widget。）

  • 避免改变所创建子树的深度，或改变子树中 widget 的类型。例如，不要根据情况返回 child 或用 IgnorePointer 包裹的 child；应始终用 IgnorePointer 包裹 child，并通过控制 IgnorePointer.ignoring 属性实现开关。这是因为改变子树深度需要重建、重新布局并重新绘制整个子树，而只改变属性只会对渲染树造成尽可能小的变更（例如，对于 IgnorePointer，完全不需要重新布局或重新绘制）。

  • 如果确实需要改变深度，可以考虑用 widget 包裹子树中的公共部分，并为这些 widget 设置在有状态 widget 生命周期内保持不变的 GlobalKey。如果没有其他 widget 适合设置该 key，可以使用 KeyedSubtree。

  • 创建可复用的 UI 片段时，优先使用 widget，而不是辅助方法。例如，如果用函数构建 widget，调用 State.setState 时 Flutter 必须重新构建该函数返回的整个包装 widget。若改用 Widget，Flutter 就能高效地只重新渲染确实需要更新的部分。更进一步，如果创建的 widget 是 const，Flutter 可以跳过大部分重建工作。

此视频进一步解释了为什么 const 构造函数很重要，以及为什么使用 Widget 优于辅助方法。

有关 widget 重建机制的详细信息，请参阅 Element.rebuild 中的讨论。

class YellowBird extends StatefulWidget {
  const YellowBird({ super.key });

  @override
  State<YellowBird> createState() => _YellowBirdState();
}

class _YellowBirdState extends State<YellowBird> {
  @override
  Widget build(BuildContext context) {
    return Container(color: const Color(0xFFFFE306));
  }
}

此示例展示了一个更通用的 Bird widget：它可以接收颜色和子级，并具有可通过方法修改的内部状态：
link 
class Bird extends StatefulWidget {
  const Bird({
    super.key,
    this.color = const Color(0xFFFFE306),
    this.child,
  });

  final Color color;
  final Widget? child;

  @override
  State<Bird> createState() => _BirdState();
}

class _BirdState extends State<Bird> {
  double _size = 1.0;

  void grow() {
    setState(() { _size += 0.1; });
  }

  @override
  Widget build(BuildContext context) {
    return Container(
      color: widget.color,
      transform: Matrix4.diagonal3Values(_size, _size, 1.0),
      child: widget.child,
    );
  }
}

按照惯例，widget 构造函数只使用命名参数。第一个参数通常是 key，最后一个参数通常是 child、children 或同等用途的参数。
