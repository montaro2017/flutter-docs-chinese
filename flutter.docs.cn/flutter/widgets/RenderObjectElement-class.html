RenderObjectElement 类 抽象

使用 RenderObjectWidget 作为配置的 Element。

RenderObjectElement 对象在渲染树中关联一个 RenderObject 组件，用于处理布局、绘制和命中测试等具体操作。

与 ComponentElement 对比。

有关 Element 生命周期的详情，请参阅 Element 中的说明。

编写 RenderObjectElement 子类

大多数 RenderObject 使用以下三种常见的子项模型：

  • 叶子渲染对象没有子项；此情况由 LeafRenderObjectElement 类处理。

  • 单个子项；此情况由 SingleChildRenderObjectElement 类处理。

  • 子项链表；此情况由 MultiChildRenderObjectElement 类处理。

不过，有时渲染对象的子项模型会更复杂，例如包含二维子项数组、按需构建子项，或有多个子项列表。在这些情况下，为配置该 RenderObject 的 Widget 对应的 Element 将是一个新的 RenderObjectElement 子类。

此类子类负责管理子项，具体而言，既要管理此对象的 Element 子项，也要管理其对应 RenderObject 的 RenderObject 子项。

专门化 getter

RenderObjectElement 通常会充当其 widget 与 renderObject 之间的中介。一般不建议专门化 widget getter；最好在各个调用点进行类型转换，避免在此特定实现之外增加开销。

class FooElement extends RenderObjectElement {
  FooElement(super.widget);

  // Specializing the renderObject getter is fine because
  // it is not performance sensitive.
  @override
  RenderFoo get renderObject => super.renderObject as RenderFoo;

  void _foo() {
    // For the widget getter, though, we prefer to cast locally
    // since that results in better overall performance where the
    // casting isn't needed:
    final Foo foo = widget as Foo;
    // ...
  }

  // ...
}

插槽

每个子 Element 都对应一个 RenderObject，该对象应作为子项附加到此元素的渲染对象。

不过，元素的直接子项不一定就是最终生成其对应 RenderObject 的对象。例如，StatelessElement（即 StatelessWidget 对应的元素）对应的是其子项（即其 StatelessWidget.build 方法返回的元素）所对应的 RenderObject。

因此，每个子项都会分配一个slot 令牌。此标识符的含义仅对当前 RenderObjectElement 节点有效。当最终生成 RenderObject 的后代准备将其附加到此节点的渲染对象时，会将该 slot 令牌传回此节点。这样，此节点就能高效地确定应将子渲染对象放在父渲染对象中的哪个位置。

父项调用 updateChild 扩展子项时，会确定该子项的 slot（见下一节）。也可以调用 updateSlotForChild 更新它。

更新子项

在元素生命周期的早期，框架会调用 mount 方法。此方法应对每个子项调用 updateChild，并传入该子项的 widget 和 slot，从而获得子 Element 列表。

之后，框架会调用 update 方法。在此方法中，RenderObjectElement 应针对每个子项调用 updateChild，传入在 mount 或最近一次 update 中获得的 Element、新的 Widget 以及 slot。这样，该对象就会获得新的 Element 列表。

如果条件允许，update 方法应尝试将上一轮的元素与新一轮的 widget 对应起来。例如，如果上一轮的某个元素使用了特定的 Key，且新一轮的某个 widget 使用相同的 key，就应将它们配对，并使用该 widget 和其新位置对应的 slot 更新旧元素。updateChildren 方法可能对此有所帮助。

应按逻辑顺序为子项调用 updateChild。顺序可能很重要：例如，如果两个子项都在其 build 方法中使用 PageStorage 的 writeState 功能，且两者都没有 Widget.key，那么第二个子项写入的状态会覆盖第一个。

在构建阶段动态确定子项

子 widget 不一定要直接来自此元素的 widget。也可以通过回调动态生成，或用其他更灵活的方式生成。

在布局期间动态确定子项

如果要在布局时生成 widget，那么在 mount 和 update 方法中生成将不起作用：此时该元素的渲染对象尚未开始布局。此时可由 update 方法将渲染对象标记为需要布局（参阅 RenderObject.markNeedsLayout），随后由渲染对象的 RenderObject.performLayout 回调此元素，让它生成 widget 并相应调用 updateChild。

渲染对象若要在布局期间调用元素，必须使用 RenderObject.invokeLayoutCallback。元素若要在 update 方法之外调用 updateChild，必须使用 BuildOwner.buildScope。

正常运行时，框架执行布局期间构建时提供的检查比普通构建更多。因此，使用布局时构建语义创建 widget 时应格外谨慎。

处理构建期间的错误

如果元素调用 builder 函数来获取子项 widget，构建过程可能会抛出异常。应捕获此类异常，并使用 FlutterError.reportError 报告。如果确实需要一个子项，但 builder 因此失败，可以改用 ErrorWidget 实例。

分离子项

使用 GlobalKey 时，其他元素可能会在此元素更新之前主动移除一个子项。（具体来说，当某个带有特定 GlobalKey 的 widget 子树从此元素移动到构建阶段中更早处理的元素时，就会发生这种情况。）发生这种情况时，系统会调用此元素的 forgetChild 方法，并传入受影响子元素的引用。

RenderObjectElement 子类的 forgetChild 方法必须从子元素列表中移除该子元素，这样下次调用 update 更新子项时，就不会再处理已移除的子项。

如果元素很多，出于性能考虑，将已遗忘的元素存储在 Set 中进行跟踪，可能比主动修改本地子项列表记录及所有 slot 标识更快。例如，可参阅 MultiChildRenderObjectElement 的实现。

维护渲染对象树

后代生成渲染对象后，会调用 insertRenderObjectChild。如果后代的 slot 标识发生变化，则会调用 moveRenderObjectChild。如果后代被移除，则会调用 removeRenderObjectChild。

这三个方法应相应地更新渲染树，分别将给定的子渲染对象附加到此元素自己的渲染对象、在树中移动，以及从树中分离。

遍历子项

RenderObjectElement 对象如果有任何子 Element，就必须在其 visitChildren 方法实现中公开这些子元素。框架的许多内部机制都会使用此方法，因此它应当足够快。测试框架和 debugDumpApp 也会使用此方法。
