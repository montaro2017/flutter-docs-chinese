Router<T> 类

用于打开和关闭应用页面的分发器。

此 widget 会监听来自操作系统的路由信息（例如应用启动时提供的初始 route、收到 intent 时获得的新 route，或用户按下系统返回按钮的通知），将路由信息解析为 T 类型的数据，再将这些数据转换成 Page 对象，并传给 Navigator。

此过程的每个部分都可以按需重写和配置。

可以重写 routeInformationProvider，以更改 route 名称的获取方式。首次创建 Router 时，会将 RouteInformationProvider.value 用作初始 route。之后，RouteInformationProvider 通知其监听器时，会被视为路由信息发生变化。

可以重写 backButtonDispatcher，以更改接收返回按钮通知的方式。它必须是 BackButtonDispatcher，即可以注册回调、也可以串联起来将返回按钮按下事件委托给子 router 的对象。回调会在用户尝试关闭当前 route（按下系统返回按钮）时调用；Router 会确保该回调触发时，消息被传给 routerDelegate，并将结果返回给 backButtonDispatcher。有些平台没有返回按钮（例如 iOS 和桌面平台），因此不会发送此通知。根 router 的 backButtonDispatcher 通常是 RootBackButtonDispatcher 实例，它使用 WidgetsBindingObserver 监听来自 SystemChannels.navigation 的 popRoute 通知。嵌套的 Router 通常使用 ChildBackButtonDispatcher，并且必须传入其祖先 Router 的 BackButtonDispatcher（可通过 Router.of 获取）。

可以重写 routeInformationParser，以更改对从 routeInformationProvider 获取的名称的解释方式。它必须实现 RouteInformationParser 接口，并使用与 Router 相同的类型参数。类型 T 表示 routeInformationParser 将生成的数据类型。

可以重写 routerDelegate，以更改对 routeInformationParser 输出的解释方式。它必须实现同样以 T 为类型参数的 RouterDelegate 接口；该接口接收 T 类型的输入，数据来自 routeInformationParser 的 T 类型数据，并负责提供一个导航 widget，将其插入 widget 树中。RouterDelegate 接口同时也是 Listenable；收到通知时，Router 会重新构建。

关于异步处理的注意事项

部分 API（尤其是涉及 RouteInformationParser 和 RouterDelegate 的 API）是异步的。

实现这些 API 的对象时，如果工作可以完全同步完成，可以考虑在相关方法中返回 SynchronousFuture。这样 Router 就能完全以同步方式继续处理，从而避免不少复杂情况。

不过，使用异步计算也完全合理，并且此 API 专为支持异步操作而设计。例如，显示 route 前可能需要加载一组图片；在 RouterDelegate.setNewRoutePath 返回前等待图片加载完成，就是合理的处理方式。

如果某个异步操作仍在进行时需要启动另一个操作，具体行为取决于当时的情况：

如果当前活动操作是 routeInformationParser 正在解析新的路由信息，则即使该操作最终完成，其结果也会被丢弃。

如果当前活动操作是 routerDelegate 正在处理弹出请求，则之前的弹出操作会立即以“false”完成，表示该请求未得到处理（这可能导致应用关闭）。

如果当前活动操作是 routerDelegate 正在处理初始 route 或推入的 route，则结果取决于新操作。如果新操作是弹出请求，即使原操作最终完成，其结果也会被丢弃。如果新操作是推入请求，则会要求 routeInformationParser 开始解析；只有当解析在原来的 routerDelegate 请求完成前结束时，原请求的结果才会被丢弃。

如果异步操作进行期间 Router widget 的委托对象身份发生变化，为简化处理，所有正在进行的异步操作结果都会被丢弃。通常认为，在 Router 生命周期内更换这些委托并不常见。

如果异步操作进行期间 Router 本身被释放，所有正在进行的异步操作结果也都会被丢弃。

上述情况发生时，不会向 routeInformationParser 或 routerDelegate 发送明确的信号，因此强烈建议 RouteInformationParser 和 RouterDelegate 实现不要执行大量计算。

应用架构设计

应用可根据自身需求包含零个、一个或多个 Router widget。

如果应用只有一个“屏幕”，或者 Navigator 提供的功能已经足够，就可以不使用 Router widget。这在桌面应用中很常见，因为子“屏幕”通常通过不同窗口表示，而不是切换当前界面。

架构较复杂的应用可能会以树状结构包含多个 Router widget，由第一个 router 负责完成全部路由解析，并将结果提供给子树中的 router。子树中的 router 不参与路由信息解析，而是直接使用第一个 router 提供的结果构建各自的子 route。

大多数应用只需要一个 Router。

Web 应用的 URL 更新

在 Web 平台上，使浏览器地址栏中的 URL 与应用状态保持同步，可以确保浏览器正确创建历史记录条目，让后退和前进按钮按用户预期工作。

如果应用状态变化导致 Router 重新构建，Router 会从 routerDelegate 的 RouterDelegate.currentConfiguration 方法以及 routeInformationParser 的 RouteInformationParser.restoreRouteInformation 方法获取新的路由信息。

如果新路由信息中的位置与当前位置不同，就会被视为导航事件；此时 PlatformRouteInformationProvider.routerReportsNewRouteInformation 会以 replace = false 调用 SystemNavigator.routeInformationUpdated，通知引擎并进而通知浏览器创建包含新 URL 的历史记录条目。否则，PlatformRouteInformationProvider.routerReportsNewRouteInformation 会以 replace = true 调用 SystemNavigator.routeInformationUpdated，使用最新的 RouteInformation 更新当前历史条目。

即使 RouteInformation.uri 未变化，也可以强制 Router 将新的路由信息作为导航事件报告给 routeInformationProvider（进而报告给浏览器）：将执行状态变化的回调传给 Router.navigate 即可。这样 Router 会使用 RouteInformationReportingType.navigate 调用 RouteInformationProvider.routerReportsNewRouteInformation，从而使 PlatformRouteInformationProvider 无论如何都会推入新的历史条目。这样可以在 URL 不变的情况下支持浏览器后退和前进按钮。例如，可以将滚动视图的滚动位置保存到 RouteInformation.state。使用 Router.navigate 更新滚动位置，会让浏览器创建一个保存新滚动位置 RouteInformation.state 的新历史条目。用户点击后退按钮时，应用会恢复到先前的滚动位置，而地址栏 URL 不变。

也可以强制 Router 忽略导航事件：在传给 Router.neglect 的回调中执行相关变更即可。Router 会使用 RouteInformationReportingType.neglect 调用 RouteInformationProvider.routerReportsNewRouteInformation，因此即使检测到位置变化，PlatformRouteInformationProvider 也会无条件替换当前历史条目。

如果要完全退出 URL 更新，可以将 routeInformationProvider 和 routeInformationParser 设为 null。通常不建议这样做，但以下情况可能适用：

  • 应用的目标平台不包括 Web。

  • 应用包含多个 router widget。只有一个 Router widget 应负责更新 URL（通常是由 WidgetsApp.router、MaterialApp.router 或 CupertinoApp.router 创建的最顶层 router）。

  • 应用不需要通过浏览器的后退和前进按钮实现应用内导航。

其他情况下，强烈建议实现 RouterDelegate.currentConfiguration 和 RouteInformationParser.restoreRouteInformation API，以便应用在 Web 平台运行时提供最佳用户体验。

状态恢复

如果 Router 配置了 restorationScopeId，且其子树已启用状态恢复，那么状态恢复期间它会恢复 routerDelegate 的当前配置。为此，操作系统终止应用前会序列化并持久化 RouterDelegate.currentConfiguration 的值。应用重启后，该值会被反序列化，并通过调用 RouterDelegate.setRestoredRoutePath 传回 RouterDelegate（默认实现只会调用 RouterDelegate.setNewRoutePath）。RouterDelegate 负责使用提供的配置信息恢复其内部状态。

为序列化 RouterDelegate.currentConfiguration 并在之后反序列化，Router 会分别调用 RouteInformationParser.restoreRouteInformation 和 RouteInformationParser.parseRouteInformation。因此，如果提供了 restorationScopeId，也必须配置 routeInformationParser。
