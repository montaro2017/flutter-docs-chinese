Navigator
description

Navigator 类

一种以堆栈方式管理一组子 widget 的 widget。

许多应用会在 widget 层级的顶部附近放置 Navigator，以便通过 Overlay 展示逻辑历史记录：最近访问的页面在视觉上位于较早页面的上方。采用这种模式，Navigator 可以通过在 Overlay 中移动 widget，实现从一个页面到另一个页面的视觉过渡。同样，也可以将对话框 widget 放在当前页面上方，以此显示对话框。

使用 Pages API

如果提供了 Navigator.pages，Navigator 会将其转换为一组堆栈式的 Route。Navigator.pages 发生变化时，会触发 Navigator 的 Route 堆栈更新，使其与新的 Navigator.pages 配置一致。要使用此 API，可以创建 Page 子类，并为 Navigator.pages 定义一个 Page 列表。还必须提供 Navigator.onPopPage 回调，以便在弹出页面时正确清理输入页面。

默认情况下，Navigator 使用 DefaultTransitionDelegate 决定路由如何进入或离开屏幕。若要自定义此行为，请定义 TransitionDelegate 子类，并将其提供给 Navigator.transitionDelegate。

有关 Pages API 的更多信息，请参阅 Router widget。

使用 Navigator API

移动应用通常通过称为“屏幕”或“页面”的全屏元素展示内容。在 Flutter 中，这些元素称为路由，由 Navigator widget 管理。Navigator 管理一组 Route 对象组成的堆栈，并提供两种管理方式：声明式 API Navigator.pages，或命令式 API Navigator.push 和 Navigator.pop。

如果用户界面符合堆栈式导航模式，也就是用户应能返回到堆栈中较早的元素，那么使用路由和 Navigator 就很合适。在 Android 等平台上，系统界面会在应用边界之外提供返回按钮，让用户返回应用堆栈中的较早路由。没有内置此类导航机制的平台，则可以使用 AppBar（通常通过 Scaffold.appBar 属性使用）自动添加供用户返回的按钮。

显示全屏路由

虽然可以直接创建 Navigator，但最常见的做法是使用 WidgetsApp 或 MaterialApp widget 创建并配置的 Router 所生成的 Navigator。可以通过 Navigator.of 获取该 Navigator。

MaterialApp 是最简单的配置方式。MaterialApp 的 home 会成为 Navigator 堆栈底部的路由，也就是应用启动时显示的页面。

void main() {
  runApp(const MaterialApp(home: MyAppHome()));
}

若要向堆栈推入新路由，可以创建一个 MaterialPageRoute 实例，并提供一个构建器函数来创建要显示的内容。例如：

Navigator.push(context, MaterialPageRoute<void>(
  builder: (BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('My Page')),
      body: Center(
        child: TextButton(
          child: const Text('POP'),
          onPressed: () {
            Navigator.pop(context);
          },
        ),
      ),
    );
  },
));

路由使用构建器函数而非子 widget 来定义自己的 widget，因为它会根据推入或弹出的时机，在不同的上下文中构建和重建。

如下面的代码所示，可以使用 Navigator 的 pop 方法弹出新路由并显示应用主页：

Navigator.pop(context);

对于带有 Scaffold 的路由，通常无需另外提供用于弹出 Navigator 的 widget，因为 Scaffold 会自动在 AppBar 中添加“返回”按钮。按下该按钮会调用 Navigator.pop。在 Android 上，按下系统返回按钮也会执行相同操作。

使用命名 Navigator 路由

移动应用通常会管理许多路由，使用名称引用路由往往最方便。按照惯例，路由名称采用类似路径的结构（例如“/a/b/c”）。应用主页路由默认命名为“/”。

创建 MaterialApp 时，可以提供一个 Map<String, WidgetBuilder>，将路由名称映射到用于创建路由的构建器函数。MaterialApp 会使用此映射为 Navigator 的 onGenerateRoute 回调生成值。

void main() {
  runApp(MaterialApp(
    home: const MyAppHome(), // becomes the route named '/'
    routes: <String, WidgetBuilder> {
      '/a': (BuildContext context) => const MyPage(title: Text('page A')),
      '/b': (BuildContext context) => const MyPage(title: Text('page B')),
      '/c': (BuildContext context) => const MyPage(title: Text('page C')),
    },
  ));
}

按名称显示路由：

Navigator.pushNamed(context, '/b');

路由可以返回值

推入路由以向用户请求某个值时，可以通过 pop 方法的 result 参数返回该值。

推入路由的方法会返回一个 Future。路由弹出时，该 Future 会完成，其值就是 pop 方法的 result 参数。

例如，若要请用户按下“确定”来确认某项操作，可以使用 await 等待 Navigator.push 的结果：

bool? value = await Navigator.push(context, MaterialPageRoute<bool>(
  builder: (BuildContext context) {
    return Center(
      child: GestureDetector(
        child: const Text('OK'),
        onTap: () { Navigator.pop(context, true); }
      ),
    );
  }
));

用户按下“确定”时，返回值为 true。如果用户离开该路由（例如按下 Scaffold 的返回按钮），返回值则为 null。

使用路由返回值时，路由的类型参数必须与 pop 的 result 类型一致。因此这里使用 MaterialPageRoute<bool>，而不是 MaterialPageRoute<void> 或不带类型参数的 MaterialPageRoute。（当然，如果你不想指定类型，也可以省略。）

弹出式路由

路由不必遮挡整个屏幕。PopupRoute 会使用 ModalRoute.barrierColor 覆盖屏幕，该颜色可以设置为半透明，使当前屏幕透显出来。弹出式路由属于“模态”路由，因为它会阻止用户与下方 widget 交互。

有一些函数可用于创建并显示弹出式路由，例如 showDialog、showMenu 和 showModalBottomSheet。这些函数会返回其推入路由的 Future，如上所述。调用方可以等待该返回值，以便在路由弹出时采取操作，或获取路由返回的值。

也有一些 widget 会创建弹出式路由，例如 PopupMenuButton 和 DropdownButton。这些 widget 会创建 PopupRoute 的内部子类，并使用 Navigator 的 push 和 pop 方法显示及关闭它们。

自定义路由

可以继承 widget 库中的路由类（例如 PopupRoute、ModalRoute 或 PageRoute）来创建自定义路由，从而控制路由显示时使用的动画过渡、模态遮罩的颜色和行为，以及路由的其他特性。

PageRouteBuilder 类允许通过回调定义自定义路由。下面的示例会在路由出现或消失时旋转并淡出其子项。与弹出式路由一样，由于设置了 opaque: false，此路由不会遮挡整个屏幕。

Navigator.push(context, PageRouteBuilder<void>(
  opaque: false,
  pageBuilder: (BuildContext context, _, _) {
    return const Center(child: Text('My PageRoute'));
  },
  transitionsBuilder: (_, Animation<double> animation, _, Widget child) {
    return FadeTransition(
      opacity: animation,
      child: RotationTransition(
        turns: Tween<double>(begin: 0.5, end: 1.0).animate(animation),
        child: child,
      ),
    );
  }
));

页面路由分为“页面”和“过渡”两部分构建。页面会成为传给 transitionsBuilder 函数的子项的后代。通常页面只构建一次，因为它不依赖动画参数（本例中以 _ 省略）。在过渡持续期间，每一帧都会构建过渡效果。

（本例中，路由的返回类型使用 void，因为它不会返回值。）

嵌套 Navigator

应用可以使用多个 Navigator。将一个 Navigator 嵌套在另一个 Navigator 下方，可创建“内部导航流程”，例如标签页导航、用户注册、商店结账，或应用某个子部分中的其他独立导航流程。

示例

iOS 应用通常采用标签页导航，并让每个标签页保留各自的导航历史。因此，每个标签页都有自己的 Navigator，形成一种“并行导航”。

除了标签页之间的并行导航外，应用仍可以打开完全覆盖标签页的全屏页面，例如新手引导流程或警告对话框。因此，需要在标签页导航上方放置一个“根” Navigator。这样，每个标签页的 Navigator 都是位于单个根 Navigator 下方的嵌套 Navigator。

在实际应用中，用于标签页导航的嵌套 Navigator 通常位于 WidgetsApp 和 CupertinoTabView widget 中，无需显式创建或管理。

以下示例演示如何使用嵌套的 Navigator 展示独立的用户注册流程。

虽然此示例使用两个 Navigator 来演示嵌套 Navigator，但也可以只用一个 Navigator 实现类似效果。

运行此示例时使用 flutter run --route=/signup，即可从注册流程启动，而不是从主页启动。

若要使用此代码示例创建本地项目，请运行：
flutter create --sample=widgets.Navigator.1 mysample 

import 'package:flutter/material.dart';

/// Flutter code sample for [Navigator].

void main() => runApp(const NavigatorExampleApp());

class NavigatorExampleApp extends StatelessWidget {
  const NavigatorExampleApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      // MaterialApp contains our top-level Navigator
      initialRoute: '/',
      routes: <String, WidgetBuilder>{
        '/': (BuildContext context) => const HomePage(),
        '/signup': (BuildContext context) => const SignUpPage(),
      },
    );
  }
}

class HomePage extends StatelessWidget {
  const HomePage({super.key});

  @override
  Widget build(BuildContext context) {
    return DefaultTextStyle(
      style: Theme.of(context).textTheme.headlineMedium!,
      child: Container(
        color: Colors.white,
        alignment: .center,
        child: const Text('Home Page'),
      ),
    );
  }
}

class CollectPersonalInfoPage extends StatelessWidget {
  const CollectPersonalInfoPage({super.key});

  @override
  Widget build(BuildContext context) {
    return DefaultTextStyle(
      style: Theme.of(context).textTheme.headlineMedium!,
      child: GestureDetector(
        onTap: () {
          // This moves from the personal info page to the credentials page,
          // replacing this page with that one.
          Navigator.of(
            context,
          ).pushReplacementNamed('signup/choose_credentials');
        },
        child: Container(
          color: Colors.lightBlue,
          alignment: .center,
          child: const Text('Collect Personal Info Page'),
        ),
      ),
    );
  }
}

class ChooseCredentialsPage extends StatelessWidget {
  const ChooseCredentialsPage({super.key, required this.onSignupComplete});

  final VoidCallback onSignupComplete;

  @override
  Widget build(BuildContext context) {
    return GestureDetector(
      onTap: onSignupComplete,
      child: DefaultTextStyle(
        style: Theme.of(context).textTheme.headlineMedium!,
        child: Container(
          color: Colors.pinkAccent,
          alignment: .center,
          child: const Text('Choose Credentials Page'),
        ),
      ),
    );
  }
}

class SignUpPage extends StatelessWidget {
  const SignUpPage({super.key});

  @override
  Widget build(BuildContext context) {
    // SignUpPage builds its own Navigator which ends up being a nested
    // Navigator in our app.
    return Navigator(
      initialRoute: 'signup/personal_info',
      onGenerateRoute: (RouteSettings settings) {
        WidgetBuilder builder;
        switch (settings.name) {
          case 'signup/personal_info':
            // Assume CollectPersonalInfoPage collects personal info and then
            // navigates to 'signup/choose_credentials'.
            builder = (BuildContext context) => const CollectPersonalInfoPage();
          case 'signup/choose_credentials':
            // Assume ChooseCredentialsPage collects new credentials and then
            // invokes 'onSignupComplete()'.
            builder = (BuildContext _) => ChooseCredentialsPage(
              onSignupComplete: () {
                // Referencing Navigator.of(context) from here refers to the
                // top level Navigator because SignUpPage is above the
                // nested Navigator that it created. Therefore, this pop()
                // will pop the entire "sign up" journey and return to the
                // "/" route, AKA HomePage.
                Navigator.of(context).pop();
              },
            );
          default:
            throw Exception('Invalid route: ${settings.name}');
        }
        return MaterialPageRoute<void>(builder: builder, settings: settings);
      },
    );
  }
}

Navigator.of 会从给定的 BuildContext 向上查找最近的祖先 Navigator。请确保传入位于目标 Navigator 下方的 BuildContext，尤其是在创建嵌套 Navigator 的大型 build 方法中。可以使用 Builder widget，在 widget 子树中的指定位置获取 BuildContext。

查找包围当前内容的路由

对于常见的模态路由，可以在 build 方法中使用 ModalRoute.of 获取包围当前内容的路由。若要判断该路由是否为当前活动路由（例如在路由未激活时将控件调暗），可以检查返回路由的 Route.isCurrent 属性。

状态恢复

如果提供了 restorationScopeId，且此 Navigator 位于有效的 RestorationScope 中，那么状态恢复时，Navigator 会重新创建当前的 Route 历史堆栈，并恢复这些 Route 的内部状态。不过，堆栈中的 Route 并非都能恢复：

  • Page-based routes restore their state if Page.restorationId is provided.
  • Routes added with the classic imperative API (push, pushNamed, and friends) can never restore their state.
  • A Route added with the restorable imperative API (restorablePush, restorablePushNamed, and all other imperative methods with "restorable" in their name) restores its state if all routes below it up to and including the first Page-based route below it are restored. If there is no Page-based route below it, it only restores its state if all routes below it restore theirs.

如果 Route 可以恢复，Navigator 会为其 Route.restorationScopeId 设置一个非 null 值。路由可以使用该 ID 保存和恢复自身状态。例如，ModalRoute 会使用此 ID 为其内容 widget 创建 RestorationScope。
