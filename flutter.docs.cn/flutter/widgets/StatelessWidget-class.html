StatelessWidget 类 抽象

不需要可变状态的 widget。

无状态 widget 通过构建一组更具体描述用户界面的其他 widget，来描述用户界面的一部分。这个构建过程会递归进行，直到用户界面的描述完全具体（例如，完全由描述具体 RenderObject 的 RenderObjectWidget 组成）。

当所描述的用户界面部分只取决于对象自身的配置信息和 widget 膨胀所在的 BuildContext 时，无状态 widget 很有用。对于会动态变化的组合（例如其内部状态由时钟驱动，或取决于某些系统状态），可以考虑使用 StatefulWidget。

性能注意事项

无状态 widget 的 build 方法通常只会在三种情况下调用：widget 首次插入树中时；widget 的父级更改其配置时（参阅 Element.rebuild）；以及它所依赖的 InheritedWidget 发生变化时。

如果 widget 的父级会定期更改该 widget 的配置，或者它依赖的继承 widget 经常变化，那么优化 build 方法的性能对于保持流畅的渲染效果非常重要。

可以采用以下几种技巧来减少重建无状态 widget 带来的影响：

  • 尽量减少 build 方法及其创建的 widget 传递性地产生的节点数量。例如，为了以特别精巧的方式放置单个子级，与其复杂地组合多个 Row、Column、Padding 和 SizedBox，不如考虑只使用一个 Align 或 CustomSingleChildLayout。与其用多层 Container 和 Decoration 实现恰到好处的图形效果，不如考虑使用一个 CustomPaint widget。

  • 尽可能使用 const widget，并为该 widget 提供 const 构造函数，以便使用者也能这样做。

  • 可以考虑将无状态 widget 重构为有状态 widget，以便使用 StatefulWidget 中介绍的技巧，例如缓存子树的公共部分，以及在改变树结构时使用 GlobalKey。

  • 如果 widget 可能因使用 InheritedWidget 而频繁重建，可以考虑将无状态 widget 拆分为多个 widget，并将树中会变化的部分下推到叶子节点。例如，如果一个包含四个 widget 的树中，最内层的 widget 依赖 Theme，可以将 build 函数中创建最内层 widget 的部分提取为独立 widget，这样主题变化时只需重建最内层 widget。

  • 创建可复用的 UI 片段时，优先使用 widget，而不是辅助方法。例如，如果用函数构建 widget，调用 State.setState 时 Flutter 必须重新构建该函数返回的整个包装 widget。若改用 Widget，Flutter 就能高效地只重新渲染确实需要更新的部分。更进一步，如果创建的 widget 是 const，Flutter 可以跳过大部分重建工作。

此视频进一步解释了为什么 const 构造函数很重要，以及为什么使用 Widget 优于辅助方法。

以下是名为 GreenFrog 的无状态 widget 子类框架。

通常，widget 还会有更多构造函数参数，每个参数都对应一个 final 属性。

link 
class GreenFrog extends StatelessWidget {
  const GreenFrog({ super.key });

  @override
  Widget build(BuildContext context) {
    return Container(color: const Color(0xFF2DBD3A));
  }
}

下一个示例展示了更通用的 Frog widget，它可以接收颜色和子级：
link 
class Frog extends StatelessWidget {
  const Frog({
    super.key,
    this.color = const Color(0xFF2DBD3A),
    this.child,
  });

  final Color color;
  final Widget? child;

  @override
  Widget build(BuildContext context) {
    return ColoredBox(color: color, child: child);
  }
}

按照惯例，widget 构造函数只使用命名参数。第一个参数通常是 key，最后一个参数通常是 child、children 或同等用途的参数。
