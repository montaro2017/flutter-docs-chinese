SemanticsAction const focus

将输入焦点移至相应的 widget。

通常，输入焦点决定哪个 widget 接收键盘输入。能够接收此操作的语义节点应设置 SemanticsFlag.isFocusable。此类可聚焦 widget 包括按钮、复选框、开关和文本字段。

收到此操作后，相应的 widget 必须将输入焦点移至自身。否则可能导致糟糕的用户体验，例如将用户输入路由到错误的 widget。尤其是文本字段，必须立即变为可编辑状态，并在需要时打开虚拟键盘。按钮必须响应来自键盘的轻触/单击事件。

widget 对此操作的响应必须具有幂等性。此操作可能会收到多次，也可能在 widget 已获得焦点时收到。

焦点行为取决于平台和所使用的辅助技术。在 Windows、macOS 和 Linux 等桌面操作系统上，移动无障碍焦点通常也会移动输入焦点。在移动设备上，无障碍焦点与输入焦点更常彼此分离。用户需要执行明确操作（例如双击以激活）来同步二者。有时，此行为可以配置。例如，在 macOS 上，用户可以在 VoiceOver 的系统设置中选择让输入焦点随 VoiceOver 焦点一起移动，或让二者保持分离。因此，widget 不应假定 didGainAccessibilityFocus 和 focus 操作会以特定组合或顺序报告。

在 Web 上，DOM 的 “focus” 事件等同于 SemanticsAction.focus。浏览器内部无法观测无障碍焦点。浏览器会根据平台功能和用户偏好，决定是否应将输入焦点移至某个元素；如果需要，就触发 DOM 的 “focus” 事件。该事件会作为 SemanticsAction.focus 转发给框架。因此，在 Web 上，引擎不会发送 didGainAccessibilityFocus。

在 Android 上，输入焦点可通过 AccessibilityAction#ACTION_FOCUS 观测到，它与无障碍焦点分开；无障碍焦点则通过 AccessibilityAction#ACTION_ACCESSIBILITY_FOCUS 观测。

另请参阅：

  • didGainAccessibilityFocus, which informs the framework about accessibility focus ring, such as the TalkBack (Android) and VoiceOver (iOS), moving which does not move the input focus.

实现

static const SemanticsAction focus = SemanticsAction._(_kFocusIndex, 'focus');
